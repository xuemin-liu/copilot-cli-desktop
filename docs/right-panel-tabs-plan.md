# Optional right-panel tabs

Status: agreed after four rounds in meeting 27AC; implemented and independently reviewed in PR #193 for v0.1.94. This supersedes the fixed Browser/Git interaction shipped in v0.1.93. The user authorized implementation, PR/fix-pr, merge, branch cleanup, and release after meeting agreement. Not every Codex behavior has been verified.

## Problem and required behavior

The layout remains left navigation, center CLI, and an optional resizable right panel. The right panel contains user-created tabs, not mandatory tool categories. The current fixed Browser/Git strip, browser selection following CLI sessions, disabled last-page close button, and backend replacement of the last closed page violate this requirement.

Direct inspection of Codex confirmed a New tab entry point, a + button, multiple tabs, browser and Changes tabs in the same strip, individual close buttons, a separate Hide tabs control, and removal of the panel after closing its last tab. Hide/reopen state retention was not tested in Codex; it is an explicit requirement for our app.

## Interaction contract

1. With no tabs, the right panel occupies no width. The app-level button is New tab. Activating it opens the panel with a neutral New tab launcher offering Browser, Git, and other registered types. A new CLI session does not create a browser.
2. With the panel visible, the app-level button is Hide tabs. It hides the panel and gives the width back to the CLI, retaining every tab, its state, active selection, and preferred width.
3. With retained tabs hidden, the app-level button is Show tabs. It restores the previous selection without creating a tab. The meeting agreed to label the restore action Show tabs. An explicit New tab command remains available.
4. The panel's + creates a neutral launcher tab. Choosing Browser replaces that launcher with one browser page; each further Browser choice creates another independent page. Choosing Git opens the current project's Git tab, or focuses its existing tab without duplicating it. General workspaces explain Git's unavailability in the launcher, without showing a permanent disabled Git tab.
5. Every tab, including launchers, Browser, and Git, has its own close button. Closing the selected tab selects its right neighbor, then its left neighbor if necessary. Closing another tab leaves selection unchanged. Closing the last tab removes the panel. A closed tab must not reappear because of a poll, session switch, or layout change.
6. Hide is not close. Tab switching and hiding retain state. Explicit browser close releases that page and its resources, respecting unsaved-page confirmation; cancel leaves it open. Explicit Git close removes its view; unsaved commit text should be recoverable as a project draft. Running Git operations finish independently of view visibility.
7. Browser tabs have page titles, loading/error state, and their own navigation controls. There is one top-level tab strip; remove the nested Browser-pages strip in the main panel. Console, Network, and DevTools remain controls within the selected browser's content.
8. CLI focus changes do not create, retarget, select, or close right-panel tabs. Project switching restores that project's panel tabs. Browsing must work with no running CLI session. Following the user's UX correction, prompt attachments automatically use the active session in this window, without a Send to selector.
9. Preserve resize and narrow-window behavior. Keyboard access supports tab navigation, adding tabs, closing the focused panel tab, and hiding/restoring the panel without intercepting unrelated CLI input. Long tab lists remain usable through overflow scrolling/menu and visible close controls.
10. Every explicit add/focus action also shows the panel. Ctrl+Shift+G adds/focuses Git and shows it; if Git is already selected and visible it hides the panel. The Git repository/worktree selection is changed only by user choice, never by CLI focus. Retain each project's Git host across project changes; Git prompt actions use the current session automatically.

## State and lifecycle design

- Introduce a typed tab collection with stable IDs, activeTabId, visibility, and width. Keep project tab collections separate from CLI session IDs. Use stable keyed hosts so switching/hiding never remounts live content.
- Use a small tool registry for labels, availability, creation, rendering, persistence, and close behavior. Ship Browser and Git adapters plus the launcher. This is an internal extension point, not a public plugin loader or speculative new tools.
- Use one browser group per project, created lazily. The group owns the existing BrowserDebug capture/control machinery and profile; each page, including script-created popups, has a stable panel-tab ID. This preserves window.opener, per-opener overrides, and shared capture without a nested tab strip. Closing an opener leaves its other pages open. Dispose the live group when its last page closes, while retaining the project's saved cookies/profile. Bound capture and CLI page listings cover that project's group; label that scope clearly.
- Page IDs and group instance IDs are distinct from session IDs and never reused. Explicit create/read/navigate/close operations are separate. Read, bounds, and polling operations must never create a group/page. Remove automatic last-page replacement. Unknown/closed IDs fail deterministically, with generation checks/tombstones preventing late async completion from recreating anything.
- Keep renderer requests validated in the main process against their owning window and project. Preserve cookie/profile isolation, permission handling, popups, certificates, DevTools overrides, and native view hiding behind other tabs/modals.
- Keep each CLI's fixed browser-control path and a distinct session token. A session control bridge owns its control.json file ({pid, port, token}) for the running session lifetime, independently of browser-group disposal. It forwards only to its explicitly bound same-project group slot; validate binding and current runtime generation for every request. Binding changes work without restart for sessions launched under the new version. Upgrading requires restarting the old desktop/CLI processes; do not promise cross-version live process migration.
- Following the user's UX correction, automatically bind browser control to the current running CLI session in its project. Session/page switches update its target; inactive sessions lose access and in-flight requests are invalidated. CLI select may choose another page without moving the UI, and routine state updates preserve that cursor. Opening a Browser tab or resuming the current CLI requires no connection picker.
- The Browser header has no Connect/Disconnect controls. Connections follow the active session in the main process, including after Resume. Reads never create pages or reveal hidden tabs. Session close/unload revokes its bridge without destroying project pages; active-session, page and runtime changes invalidate in-flight commands, including after an async permission response.
- The main window owns project tabs; a browser page's dedicated pop-out may own that page. Pop-out/return transfers the same page ID; closing that window closes its page (with beforeunload), while Return moves it back. Detached CLI session windows offer Show browser in main window rather than retaining a second browser container. Session window ownership must not transfer project browser groups.
- In separate-profile mode, each project has a new persistent browser profile ID owned by its manifest, shared by that project's pages; separate projects stay isolated. Shared mode continues using the configured shared profile. Add active project-manifest profile IDs to startup prune keep-lists. Session cleanup never clears project storage. Closing tabs releases live resources but does NOT sign the user out. Old session jars stay with their old sessions until normal cleanup and are not merged; the migration notes explain that new separate project profiles require signing in again.
- Local Overrides becomes a project-browser setting initialized from Settings' browserOverrides default and persisted in the project manifest. Remove its new-session-dialog choice. Legacy session privateOverrides remains readable for old data cleanup but does not override project-browser settings or merge folders. Private uses the project's own DevTools partition; shared retains existing shared-default behavior. Expose the setting in browser settings with scope and next-group-open effect clearly stated; changing it never closes live pages automatically.
- Capture records retain pageId. Each tab's Console/Network view filters to that page; record/preserve/clear controls are explicitly labeled as affecting all project browser pages. Per-page scopes must also apply to CLI capture reads and request detail lookup.
- Allow at most 32 live browser pages across all project groups, including popups. Reject additional creates with a useful message listing page counts by project; never silently suspend or discard a live page. Inactive-project pages retain state but native bounds are hidden. Popup placement depends on the opener page: detached openers produce detached pages; docked openers produce panel tabs.
- Explicit close waits for main-process destruction before removing the tab. A beforeunload cancel preserves tab and selection; a close failure remains visible. App quit and workspace removal use explicit forced disposal (as current lifecycle shutdown does), not repeated page dialogs. Workspace removal revokes bindings/disposes runtimes but deletes no manifest/profile until its config write succeeds. A failed config write leaves recoverable tab metadata/profile data intact for rollback. On success remove the manifest and private project profile (or drop its keep-list entry for startup pruning); never clear the shared profile. Re-adding a removed workspace creates a fresh private profile and requires signing in again. There is no user-facing Restore workspace feature.
- Persist a versioned project tab manifest (type, stable ID, safe restoration data, order, active selection, visibility). Browser processes/DOM state are retained during hide, not across app restarts; restart restores saved URLs lazily. Do not persist credentials or transient page contents.
- Migration starts with zero tabs: a saved URL proves past navigation, not intent to keep a tab open. Copy the old dock width as the initial project width, and offer valid saved URLs/history as Recent choices in the launcher. Never delete old preferences/profile data during migration. Do not persist launcher tabs across restart.
- Automation does not silently reveal hidden tabs. State/navigation requests may work hidden; rendering-dependent screenshot/pick/testing operations return an actionable show-tab error when visibility is required. Hidden permission requests must identify the project/page; preserve the existing explicit permission approval boundary. Hiding continues to stop Testing/picking and shows an interruption notice on return.

## Implementation sequence

1. Agree on the interaction contract, especially hidden-panel labels, project scope, automation binding, close behavior, and migration.
2. Build the tab state machine, registry, persistence/migration, launcher, tab strip, and panel controls with lightweight content fixtures. Exercise zero/one/many tabs before browser integration.
3. Refactor browser resource lifecycle and validated IPC around explicit IDs, including truly closing the last page and handling late requests after close.
4. Integrate Browser and Git; route existing toolbar/shortcut commands into add/focus/show operations; remove mandatory Browser/Git slots and automatic session-follow behavior.
5. Integrate automation bindings, popup/pop-out/return behavior, project restoration, and lifecycle cleanup. Update documentation and migration notes.
6. Demonstrate the real interaction, run regression checks, then review the resulting PR. Review must assess the user actions below, not just whether the implementation matches its own tests.

## Acceptance checks

- A fresh workspace and a newly started CLI session have zero browser resources and no forced right panel.
- Add Browser A, Browser B, and Git into one tab strip; each is selectable and independently closable. Adding Git again focuses the existing Git tab.
- Close inactive B: A stays selected. Close selected A: the defined neighbor is selected. Close the final tab: panel disappears and resource count reaches zero after cleanup.
- Hide/show restores order, selected tab, browser page/form state, Git draft, and panel width; it creates no tabs and does not restart terminals.
- Session focus, side-chat changes, unload/resume, and session deletion do not recreate closed browsers or retarget open ones. Browsing works with no CLI process.
- Project switching, app restart, and migration restore only the intended tabs without cross-project state leakage or phantom browsers.
- Browser beforeunload cancellation works; close during loading/polling/automation and pop-out/return races cannot resurrect a page. Validate actual native WebContents and control endpoint cleanup, not only DOM absence.
- Existing browser automation, profile isolation, native bounds/modal hiding, permissions/certificates, and Git operations remain correct under the new ownership model.
- Closing a CLI session leaves project browser cookies and pages intact. Startup prune keeps active project profile data. Workspace removal rolls back without deleting profile data if config persistence fails, and removes private project data only after success.
- A script popup appears as its own top-level tab with window.opener and overrides intact; closing its opener does not close it. The global page limit includes popups and inactive projects.
- A CLI started before a browser exists automatically gains access when current and a page is opened. Inactive or ended sessions cannot reach any group. Session tokens remain distinct.
- User page selection and session changes update the active connection cursor; CLI select does not change the UI. Reopening the final page targets the new page automatically. Group disposal leaves the running session control file intact, without recreating resources from a read.
- Keep the existing numeric runtime page IDs in CLI tabs/select/capture for command compatibility, mapping them explicitly to persistent panel-tab IDs. Runtime IDs are valid only in their current group generation; restart/resume reconnects automatically and requires a fresh tabs listing. Visibility-dependent errors name the target page so the user can select it without implicitly revealing a page.
- The new-session dialog no longer offers Local Overrides; the project-browser setting preserves private/shared behavior at its documented scope. Console/Network UI and CLI read only the intended page; group-wide capture controls are clearly labeled.
- Keyboard-only operation, many tabs, and narrow widths remain usable.

## Review questions

1. Is Show tabs appropriate for restoring hidden tabs, reserving New tab for adding a launcher? The user's named Codex controls must not be copied with misleading behavior.
2. Is one Git tab per project sufficient while allowing multiple independent browser tabs?
3. Should the session automation binding select a browser explicitly through UI/CLI, and what compatibility behavior is needed for existing browser commands?
4. What existing browser history/settings reliably identify explicitly used pages for migration?
5. Which lifecycle paths could still recreate a closed browser or tie it to a CLI session?
